# Working notes, 2026-11

### 2026-11-05: the target is confirmed, so the next boot drops the QUP

Offline check against whyred's own kernel
(`Whyred-Dev/android_kernel_xiaomi_sdm660`, branch `lineage-15.1`):
`arch/arm/boot/dts/qcom/sdm660-mtp_whyred.dts` includes
`synaptics-dsx-i2c.dtsi`, and that file puts the controller on **`&i2c_1`**:

    &i2c_1 {
        status = "ok";
        synaptics_dsx@20 { reg = <0x20>; interrupts = <67 0x2008>;
                           vcc_i2c-supply = <&pm660_l11>; ... };
        novatek@62 { reg = <0x62>; novatek,reset-gpio = <&tlmm 66 ...>;
                     novatek,irq-gpio = <&tlmm 67 ...>; };
    };

So `0x0c175000` (BLSP1 QUP1), address `0x20`, IRQ GPIO 67 and VDDIO PM660
LDO11 are confirmed from the phone's own DT, not guessed. GPIO 66 is the
Novatek reset; the DSX reset goes through pinctrl (`ts_reset_suspend`), so
the probe's GPIO 66 pulse is only a fallback. Accessing `0x0c175000` is not an
address mistake, and moving to another QUP would just read an unused bus.

Decision for the next boot: **no QUP**. Touch already worked in recovery on
2026-10-30 (real `ABS_MT_*` events, F12 present), and no iOS boot has ever
reached `dsx_diag()`: the probe runs the QUP init first and dies there, so the
0189 framing matrix has only ever run against the *bootloader-mode* part. Pack
a bit-bang-only image (`SWEETI2C=0 OUT_IMAGE=images/shim-boot-touch-bitbang.img
bash tools/build-touch-diag.sh <RUN>`) and boot it: it cannot touch the QUP
window, so it cannot kill the SoC, and it prints the framing matrix plus the
F12 poll against the app-mode controller. If `page|a1` is accepted there,
touch reports can be read over the bit-bang without the QUP at all; the QUP
then becomes a performance fix, not a blocker. Porting ginkgo's driver stays
deferred: ginkgo is QUPv3 and its useful part (F01/F12 report parsing) comes
*after* this step.

### Ring 0197 (2026-11-05): the matrix finally ran, and app-mode reads are zero

The bit-bang-only image (`sweeti2c=0`, kernel `6bb8de5`) booted safely and
returned to fastboot by itself. The ring was pulled from recovery:

    WHYRED TOUCH: reset pulse low 20 ms, high 200 ms + 50 ms settle
    WHYRED TOUCH: ack 0x20
    WHYRED TOUCH: framing matrix over bit-bang
    WHYRED TOUCH: dsx page|a1 [0x00e9] 00 00 00 00 00 00 |......|
    WHYRED TOUCH: frame page|a1 streams
    ... every framing the same; a1 gives 00 04 00 00 00 00 ...
    WHYRED TOUCH: no framing addressed the chip, keeping page|a1
    WHYRED TOUCH: dsx no F01 in the page table
    WHYRED TOUCH: no F12 data base, cannot poll touch

The address and reset are right (0x20 ACKs), but every data bit reads 0. That
is the signature of a **missing external pull-up**, not a wrong framing: the
ACK is an actively driven low, while a `1` bit is a released line that needs
the pull-up to rise. The external 2.2k pull-ups sit on `pm660_l11`
(`vcc_i2c-supply`), and XNU has no PM660 SPMI driver, so only the weak
internal TLMM pull-up is left. At the old 10 us half bit the line does not
settle before the sample; the `a1` framing's lone `0x04` is the one bit that
did. This also explains why the bootloader-mode read worked in 0188: that
part drives its stream differently, and the internal pull-up is enough when
the slave is doing the work.

The 0184 bit-bang was slowed to `TOUCH_I2C_DELAY_US = 100` (~5 kHz) for the
next boot; 0199 (below) reverted it to 10, because 5 kHz read all zero. The
scan is still only ~200 ms for the whole `0x08..0x77` range at 5 kHz. When
the phone is next in recovery, read
`/sys/kernel/debug/regulator/regulator_summary` to see whether LDO11 is on
after ABL; that turns the pull-up hypothesis into a measurement. Ring 0199
answered the timing question: 100 us read all zero too, so the half bit is
back at 10 us and the zeros are a chip state, not a rise-time problem.

A third dwell now sits immediately before the first SE write, with
`WHYRED I2C: QUP mapped, resetting the SE` printed first, so a ring that stops
after `clocks on` but before that line is the SE's address window, while a ring
that stops right after it is the SW reset itself.

A full diagnostic boot is also ~5 minutes (50 kHz bit-bang scan, framing
matrix, DSX dump, 15 s panel hold), not the 2 minutes the earlier cycles
assumed. `tools/touch-cycle.sh` waits up to 420 s now; the 20:08/20:47 boots
that looked like hangs had in fact returned to fastboot just after the old
180 s window.

The 20:08 boot on 2026-10-31 showed the hole in that: the reset sits at the
*end* of the probe, so a stall in `sweet_clocks_on()` or the first QUP access
never reaches it. USB stayed down for more than four minutes and the phone
needed a 15 s Power hold, which is exactly what these unattended cycles are
supposed to avoid. The probe now arms a watchdog thread before the first
clock write: it sleeps `sweetouchwatchdog` seconds (default 240) in chunks and
then calls the same `whyred_reboot_bootloader()`. It runs on another core, and
both IMEM and PS_HOLD sit outside the BLSP window whose access stalls, so a
locked bus cannot take the escape hatch down with it.

### Why userspace could not answer it

`/dev/i2c-1` (c175000.i2c, `MSM-I2C-v2-adapter`) is present and writes to an
absent address fail honestly with `ENOTCONN`, but *every* read returns zeros,
including a read with no register write at all, while the kernel driver reads
`buildid` 2788281 fine. A matrix tool over `/dev/i2c-1`
(`addr1+read`, `page|addr1+read`, `page+addr1+read`, `addr2+read`,
`page+addr2+read`, read-only) returned six zeros for all seven variants, so the
i2c-dev path cannot be used as an oracle here. `/dev/mem` does not exist and
there is no tracefs/dynamic-debug in the recovery kernel, so the bit-bang has
to be exercised from XNU.

### 2026-11-06: the recovery bus is healthy, and reset is an XNU-only variable

A raw I2C probe (`tools/i2cprobe.c`, static aarch64, push to
`/data/local/tmp`) ran against the recovery's own QUP at 400 kHz. It sends the
page select (`FF <page>`) as its own transaction, then the one-byte register
address plus a repeated start, exactly like the vendor driver:

    /data/local/tmp/i2cprobe 1 0x20 0 0xe9 6 0

Results, in order:

* With the recovery screen off (driver suspended: `synaptics_rmi4_suspend ...
  SUSPEND END`), every read returned `00 00 00 00 00 00`. Wrong addresses on
  the same bus fail with `ENOTCONN`, so 0x20 really ACKs while returning zeros.
* Writing `1` to `/sys/class/input/input2/reset` made the driver try a reset;
  its PDT scan failed (`Failed to find F01/F35`), but for about a second after
  that the raw probe read **real bytes**: `0xe9 -> 56 36 00 01 a7 b0`,
  `0x0000 -> 01 10 00 10 00 70 01 00`, `page 1 -> 01 00 01 00 f0 00 00 22`.
* Three seconds later the same reads returned `ff ff ff ff ff ff`; later
  again, `00`. So the part ACKs in several states and drives neither 0s nor
  real data in most of them. Ring 0197's all-zero matrix is therefore **not
  proof that the bit-bang is wrong**; it is a chip state that the QUP
  reproduces.

The decisive difference between XNU and the working recovery kernel is the
reset line. whyred's live DT touch node has **no `synaptics,reset-gpio`
property** (`compatible, interrupts, pinctrl-0/1, reg, synaptics,irq-gpio,
synaptics,irq-on-state, power/reset delays, vcc_i2c-supply` only), so the
vendor driver never drives GPIO66 at all. Recovery's `ts_active` pinctrl
leaves it as an input with a pull-up; nothing pulses it. XNU's `dsx_reset()`
drives it push-pull low for 20 ms on every diag boot, which is a variable the
working kernel never exercises and may be what parks the part in the state
that reads zeros.

`tools/build-touch-diag.sh` now takes `SWEETRESET=0` to drop
`sweetouchreset=1` from the payload command line. Two images are ready:
`images/shim-boot-touch-norst.img` (kernel `6bb8de5`, 10 us half bit,
sha256 `b3e25ae5d4d6abee35557cf4d19125114efc33a2b745bcddc5bff6d86536182b`) and
`images/shim-boot-touch-norst-5k.img` (kernel `275f3b0`, 100 us half bit,
sha256 `9f2adae7fe83e8930989164cb3bb3a42bff757bee63d931077d0273f7f816d7b`),
both with `sweeti2c=0 sweetouchreset=0`. Boot the 10 us one first: it changes
only the reset variable. If the matrix reads a real PDT without the reset
pulse, the pulse is the problem and the 5 kHz theory is moot. If both still
read zero, try the 5 kHz image and then a full power-off before booting, since
a SoC reboot does not remove power from the DSX (`pm660_l11` stays on).

### Ring 0198 (2026-11-06): without the reset pulse the chip answers with real bytes

Powered off, then `fastboot boot whyred-touch-norst.img` (kernel `6bb8de5`,
`sweeti2c=0 sweetouchreset=0`). The ring has no `reset pulse` line, and the
matrix finally reads non-zero data:

    WHYRED TOUCH: ack 0x20
    WHYRED TOUCH: scan done, 1 address(es) acknowledged; sda 1 scl 1
    WHYRED TOUCH: dsx page|a1   [0x00e9] 12 0a 29 00 8f d4
    WHYRED TOUCH: dsx page+a1   [0x00e9] 81 04 03 03 04 05
    WHYRED TOUCH: dsx page|a2be [0x00e9] 05 01 01 01 0e 0f
    WHYRED TOUCH: dsx page|a2le [0x00e9] 0f 04 01 00 00 01
    WHYRED TOUCH: dsx a1        [0x00e9] c7 11 12 33 13 49
    WHYRED TOUCH: dsx a2be/a2le [0x00e9] 00 00 00 00 00 00
    WHYRED TOUCH: no framing addressed the chip, keeping page|a1
    WHYRED TOUCH: dsx no F01 in the page table

So the zeros in 0197 were the reset pulse (or the warm boot that kept the DSX
powered), not the bus. Every framing now gets *distinct* bytes, but every one
still fails the stability test (two reads at `0x00e9` differ, so the address
phase is ignored and the part streams). The `a2be`/`a2le` framings read all
zero, which means those address bytes probably never matched.

The remaining suspect is edge rise time. The bus has only the internal TLMM
pull-up, and `i2c_write` releases SDA for a `1` and samples the slave's SCL
edge after `TOUCH_I2C_DELAY_US` = 10 us. A weak pull-up plus bus capacitance
gives a rise time on that order, so the slave can latch a master `1` as `0`
while the master's address ACK still works. The address byte `0xe9` has four
`1` bits and is exactly the byte that must survive: if it arrives as `0x69`
or similar the slave still ACKs and simply streams from the wrong register.
The 5 kHz image (`images/shim-boot-touch-norst-5k.img`, kernel `275f3b0`) is
the next single-variable test, again after a full power-off.

### Ring 0199 (2026-11-06): 5 kHz reads zero, and the recovery QUP cannot address the chip either

Same no-reset image at a 100 us half bit (`sweeti2c=0 sweetouchreset=0`, kernel
`275f3b0`). Every framing read `00 00 00 00 00 00`. So the 5 kHz theory is
dead: 10 us is the only setting that has ever produced bytes, and timing is
not the variable.

That boot was a warm reboot (the DSX keeps `pm660_l11` across SoC resets), and
the raw probe in recovery then reproduces the same wall from the known-good
QUP:

* Modes 0, 1, 2 (page select / separate start, 1- or 2-byte address) and modes
  4, 5 (address + dummy 0x00) and 6, 7 (plain read, with and without page
  select) all returned `00 00 00 00 00 00`.
* Writing `1` to `/sys/class/input/input2/reset` fails with `EINVAL`, but the
  driver still runs `synaptics_rmi4_reset_device`; it logs
  `query_device: Failed to find F01` / `Failed to find F35`. In the second
  after that, six back-to-back reads of `0x00e9` on the QUP returned six
  *different* blocks: `56 36 00 01 a7 b0`, `01 10 00 10 00 70`,
  `01 00 01 00 01 00`, `f0 00 00 22 00 ff`, then `ff` for the rest. Even the
  vendor bus cannot make the address phase land in this state.
* Unbinding and rebinding `1-0020` also fails the same way, so this is not the
  raw probe racing the driver.

At boot (0.92 s) the same driver did find F01/F12 and filled
`/sys/class/input/input2/productinfo`, `buildid` and `fwblockcount`; it
suspends at 3.25 s with `enable_wakeup_gesture is on`, and from then on every
PDT scan fails. The chip therefore enters a sleep state on suspend and does
not accept addressed reads until something wakes it - normally the panel
itself, through IRQ GPIO 67. A warm reboot inherits that sleep. That is the
`00` matrix in 0197 and 0199.

This does **not** yet explain 0198: after a full power-off the chip was awake
and returned real (if unstable) bytes, so the bit-bang's address phase still
has its own problem. The next diagnostic adds `page|a1dup` (the page select,
address byte, and a dummy `0x00` before the repeated start) and prints both
reads on an unstable framing, so a streaming pointer (whole block shifts) can
be told from one lost address bit (one byte changes).

### 2026-11-06: the PDT is intact, and the part is streaming, not misaddressed

After ring 0199 the recovery QUP was probed once more, this time with a loop
that read `0x00e9` every 2 s for 150 s (75 reads). The result separates the
states cleanly:

* Reads 1-10: `00 00 00 00 00 00` (the sleeping state).
* Reads 11-16: a coherent stream. Concatenating the six-byte blocks gives

      00 00 ff ff ff ff | ff ff ff 27 00 09 | 00 21 34 2f 26 0d |
      04 01 01 4c 00 13 | 06 01 12 00 00 00

  which segments, at the right offset, into exactly the page descriptor table:

      27 00 09 00 21 34   F34  query 0x27 cmd 0x00 ctrl 0x09 data 0x00 intr 1
      2f 26 0d 04 01 01   F01  query 0x2f cmd 0x26 ctrl 0x0d data 0x04 intr 1
      4c 00 13 06 01 12   F12  query 0x4c cmd 0x00 ctrl 0x13 data 0x06 intr 1
      00 00 00 00 00 00   end of PDT

  So the controller is alive, its firmware/PDT is intact, and F12 (2D touch)
  is present with data base `0x06`. This is the first full PDT ever read from
  this phone.
* Reads 17+: every value becomes random (`ff 21 32 17 24 08`, ...) and finally
  all `ff`. That part is an artefact of the experiment: unbinding `1-0020`
  releases `vcc_i2c` (`pm660_l11`) in `synaptics_rmi4_remove`, which also
  powers the external I2C pull-ups, so the bus afterwards floats. The random
  reads and the final `ff` say nothing about the chip.

Two conclusions. First, the address phase is **not** landing: 75 reads of the
same `0x00e9` walk the register map six bytes at a time instead of repeating
the F34 entry, and this happens on the known-good QUP too. The part is in a
streaming mode that ignores the address write. Second, the stream still
contains the whole PDT, so a future probe can read it by reading a long block
and parsing for `fn_number`, without needing the address phase at all.

The streaming mode is almost certainly the chip's own bootloader/ROM state:
the vendor driver finds F01/F12 at 0.92 s after power-up, then suspends at
3.25 s with `enable_wakeup_gesture is on`, and from then on no PDT scan
succeeds. A warm reboot inherits it. This is the `00` matrix of 0197/0199, and
it is not a bit-bang bug. Ring 0198 (cold boot, no reset) read real but
unstable bytes because the part was in this same streaming state, not because
the bit-bang was mis-sampling.

What still has to be explained is why a cold boot does not stay in app mode.
The recovery driver proves the part is in app mode right after power-up, so
the next test must probe before anything suspends it: cold boot straight into
XNU (which never suspends the DSX) and read a long block, not six bytes.

### 2026-11-06: "streaming" may just be the page select, not the chip

The conclusion above (address phase ignored, part in a bootloader/ROM stream)
has one hole: the vendor driver works, and it reads the F12 data base
(`0x0006`) over and over during a touch. If every address write were ignored,
continuous touch could not work. So the part is addressable in app mode, and
our probe is doing something the driver never does.

There are exactly two differences between `tools/i2cprobe.c` mode 0 and the
vendor's read path:

1. **Page select on every read.** The vendor's `synaptics_rmi4_i2c_set_page()`
   writes `FF <page>` only when the page changes, and initialises
   `current_page` to `0xFF`. Our probe, and the XNU diag, write `FF 00`
   before *every* read. The vendor code goes out of its way to avoid that.
2. **The same register twice in a row.** The self test in patch 0189 reads
   `0x00E9` twice and expects the same six bytes. The vendor never does that;
   its PDT scan walks `E9, E3, DD, D7, D1`, and its later reads alternate
   between `0x2F/0x0D/0x26/0x2F/0x4C/0x13/0x06`.

A test that tells the two apart without a reboot: read `E9`, then `E3`, then
`E9` again.

* address phase works, page select is the bug: `F34, F01, F34`
* pure stream: `F34, F01, F12` (the next records in memory)
* all `00`: the part is asleep; touch the panel once first

`tools/recovery-dsx-test.sh` automates this on the recovery QUP (mode 2 = the
vendor's framing, no page select; mode 0 = page select every read) and first
forces the driver back to continuous reporting mode with
`echo 0 > wake_gesture; echo 0 > suspend`. Keep the driver bound: unbinding
it disables `vcc_i2c` and the pull-ups, after which every read is floating.

If the `F34, F01, F34` result comes back, the fix is small: XNU's
`dsx_read_f()` must cache the page and send `FF <page>` only when it changes,
exactly like `synaptics_rmi4_i2c_set_page()`. Do not spend another ring on a
long-block parse until this test has run.

### 2026-11-10: 0190 was never applied, and the page cache lands

The `F34, F01, F34` fix is now in the tree, but it came with a second bug
worth recording: **0190 has not been in any kernel since 0189 changed the
file.** dxb runs `git apply --check` and only warns when a patch fails, so
the QUP hunk was skipped silently. Its context still said

```
	if (frame == DFRAME_PAGE_A1 || frame == DFRAME_PAGE_A2_BE ||
	    frame == DFRAME_PAGE_A2_LE) {
```

while 0189's `DFRAME_PAGE_A1_DUMMY` had already turned that into a three-line
condition. Every QUP image since then was actually the bit-bang build with
`sweeti2c=1` parsed and never used, which matches the rings where the QUP
never printed its first line.

Fix:

1. Rebuild the post-0189 file by applying 0184..0189 to a scratch tree, then
   regenerate `0190` as a diff from that exact file (hunk offsets
   `@@ -429,6 +496,10 @@` and the `DFRAME_PAGE_A1_DUMMY` context line).
   `tests/run_tests.sh` now asserts both, so this cannot regress silently.
2. New `0191-whyred-touch-page-cache.patch`: `dsx_read_f()` and `dsx_read_q()`
   cache the selected page in `dsx_page` and send `FF <page>` only when it
   differs, like `synaptics_rmi4_i2c_set_page()`. The cache is dropped on a
   controller reset and when the QUP takes the bus. It is set only after the
   page write returns success, so a failed select is retried instead of
   being remembered.
3. The workflow's "a critical patch was skipped" guard stopped at `018[0-9]`,
   so a skipped 0190/0191 did not fail the build. It now matches `01[89][0-9]`.

The next ring should only be taken after this series builds, with
`tools/build-touch-diag.sh` and the E9/E3/E9 test deciding between the three
outcomes above.

### 2026-11-10: the pulled ring repeats the first PDT record, then advances

The ring pulled from recovery (`tools/sweet-log-pull.sh`, flush #27) was taken
with `sweeti2c=0 sweetouchreset=0`, so it is the bit-bang image, not the QUP
one. The addressing matrix on that run is sharper than "unstable":

    WHYRED TOUCH: page|a1 unstable 27 00 09 00 21 34 -> 2f 26 0d 04 01 01

Both reads are exactly page-descriptor records: `27 00 09 00 21 34` is the
F34 entry at `0x00E9`, and the second read is the F01 entry that follows it at
`0x00E3`. So the first addressed read after the page select lands correctly,
and the *next* read of the same register returns the next six bytes. The
address byte itself, the page select and the bit-bang transmitter are all
fine; the part keeps a read pointer that advances by the read length and
ignores the following address write. Every later framing in the matrix reads
further down that stream, which is why it looks random.

The recovery QUP was then probed on the live vendor driver. `synaptics_rmi4_resume`
runs (the driver logs `RESUME END`) but its own reads hit `I2C retry 1/2`, and
`tools/recovery-dsx-test.sh` (E9, E3, E9 in modes 2 and 0, three rounds) returns
`00 00 00 00 00 00` for every read. That is the sleeping state the 2026-11-06
notes describe: the chip only accepts I2C reads while the panel is awake, and
it cannot be woken over adb.

Consequence for the next boot: the QUP image (`sweeti2c=1 sweetouchreset=1`,
kernel `76ca451` = run 42743027729, which does contain the regenerated 0190 and
the 0191 page cache) has never been booted. It is the only artifact that uses
the same hardware I2C block as the vendor driver, so it is the next ring.

### 2026-11-10: the QUP control probe is what took the phone off USB

The ring pulled after the failed cycle (`flush #4`, cmdline `sweeti2c=1
sweetouchreset=1`) stops on

    WHYRED I2C: clocks on, RCG cfg 0x00000001 cmd 0x00000002, apps 0x00000001
    WHYRED I2C: probe QUP2/QUP3 windows (controls)

and nothing follows. So the hang is the *control* read of the QUP2 window at
`0x0c176000`, not QUP1: reading an unclocked BLSP1 sibling stalls the NoC, and
the 300 s watchdog was the only way back. The window probe is now opt-in
(`sweetqupctl=1`) and the default boot never touches a sibling window. This
also explains the phone vanishing from `lsusb` during the cycle.

The same ring, plus the live recovery probe, still says the I2C problem is the

### 2026-11-10: 0192 reads a whole page instead of addressing it

The fix for F12 follows from ring 0201 rather than from a new guess: the first
addressed read lands on `0x00E9` and the second returns the next six bytes, so
the part keeps one read pointer and advances it by the read length. Addressing
cannot be repaired from the master side, but a sequential pointer is exactly
what a long read wants.

`0192-whyred-touch-page-read.patch` reads 128 bytes from `0x0000` in one
transfer, places the window with the known F12 page-descriptor record
(`4c 00 13 06 01 12`), computes `window base = 0x00E9 - offset`, and turns
that into `f12off = 0x0006 - base`. It prints the whole window, the record
offset, the computed F12 data offset and ten polls of that byte 300 ms apart,
so a finger on the panel shows up as a changing byte with bit 7 set.

If the window comes back all zero the part is asleep; if it comes back
sequential but without the record, the window started too far along and the
next step is a longer read, not another framing.

### 2026-11-11: 0192 confirmed the pointer, 0193 spends the first read

The console image built from 0192 booted and wrote flush #15 of the ring. It

visible. F12 is taken from `fn5 & 0x3f == 0x12`, matching `dsx_identify`. If the
table is F34+F01 only (the flash-programming table), the probe pulses reset once
and scans again. It then polls F12 through a page-0 window at the data base the

### 2026-11-11: 0193 found the record off the grid; 0194 reads four entries

The 0193 console image booted and pulled flush #16 of the ring
(`/tmp/opencode/touchlog/pdt0193.log`, 20236 bytes). The 256-byte PDT window
starts like this:

    27 00 09 00 21 34  2f 26 0d 04 01 01  81 4c 00 13 06 01
    12 0a 29 00 8f d4  1e 08 00 40 38 0e  0f 15 c7 11 12 33

The first 36 bytes are byte-identical to what the vendor driver's `0x00E9`
reads returned in 0188, so the bit-bang transfer itself is right. The F12
record `4c 00 13 06 01 12` is plainly there, at offset 13, behind one stray
`0x81`. That byte shifts it off the 6-byte grid: the scan counted 41
"entries" (it counted the register bytes after the end marker too), never
matched `fn == 0x12`, and because `entries` was 41 the `entries <= 3` reset
retry never fired. `dsx_identify()` then ran after the framing matrix, started
wherever that left the stream, and printed `dsx no F01 in the page table`.

Two conclusions:

* The table is three records long - F34 at `0xE9`, F01 at `0xE3`, F12 at
  `0xDD`, then the end marker. Reading 256 bytes reads four times more than
  the table and mixes register data in after the marker.
* The F12 record must be accepted **at any offset**, because the chip can put
  one stray byte in front of it. The record itself names the data base.
* `dsx_identify()` was also decoding the entry with the wrong fields:
  `f01_query = b[0]<<8|b[1]`, `f12_ctrl = b[3]`, `f12_data = b[4]`. With the
  authoritative record `4c 00 13 06 01 12` (query `0x4c`, cmd `0x00`, ctrl
  `0x13`, data `0x06`, intr `0x01`, fn `0x12`) that made the touch test poll
  `0x01` instead of F12 data `0x06`. The fields are `e[0]`, `e[2]`, `e[3]`.

`0194-whyred-touch-page-reselect.patch` therefore:

* reads exactly 24 bytes (four records) from `0x00E9` and dumps them in one
  line, so the whole table is visible;
* forces `FF <page>` before that read (`dsx_page = -1`), because 0191 caches
  the page and the cache hides whether the write re-arms the pointer;
* parses `query = e[0]`, `ctrl = e[2]`, `data = e[3]`, `fn = e[5] & 0x3f`,
  records `f12_page`, and falls back to finding `4c 00 13 06 01 12` at any
  offset;
* runs the E9/E3/E9 test the 2026-11-10 notes asked for: a cached read of
  `0xE9` (no `FF`), then `0xE3`, then a forced read of `0xE9` (with `FF`). If
  the last one returns the F34 entry again, the page select is what re-arms
  the pointer and every later read can be prefixed with it;
* polls F12 at `(page << 8) | data`, eight bytes, forcing `FF <page>` before
  every one of the 12 samples, so each sample gets the first-read chance;
* fixes the `dsx_identify()` field offsets, and overrides `dsx.f12_*` with the
  scan result because `dsx_identify()` runs after the matrix and is not a
  reliable source;
* removes **both** GPIO-66 resets from the retry paths. whyred's DT has no
  `synaptics,reset-gpio`; GPIO 66 is the Novatek reset, and ring 0197 showed
  that pulsing it parks the DSX in an all-zero state.

Recovery-side evidence from the same day, on a fresh OrangeFox boot:

    udg_scan_pdt: Failed to find F12
    buildid 2788281   fwblockcount 432   configblockcount 16
    productinfo 0x01 0x00

Reads work (`buildid`, `fwblockcount`), writes do not: the F01 reset and even

### 2026-11-12: 0194 lands the PDT, IRQ moves on a tap, and the part is in LPWG

Ring 0194 (flush #181, console image `shim-boot-touch-pdt24-console.img`)
settles the framing question and opens a different one:

    first read: 24 bytes from 0x00e9 via page|a1
    dsx pdt [0x00e9] 27 00 09 00 21 34 2f 26 0d 04 01 01 81 4c 00 13 06 01 12 0a 29 00 8f d4
    first read entry 0 query 27 cmd 00 ctrl 09 data 00 intr 21 fn 34
    first read entry 1 query 2f cmd 26 ctrl 0d data 04 intr 01 fn 01
    first read entry 2 query 81 cmd 4c ctrl 00 data 13 intr 06 fn 01
    first read entry 3 query 12 cmd 0a ctrl 29 data 00 intr 8f fn 14
    first read F12 record at offset 13
    first read: 4 entries, F12 found at page 0 query 0x4c ctrl 0x13 data 0x06
    dsx repeat cached [0x00e9] 1e 08 00 40 38 0e
    dsx then e3 [0x00e3] 0f 00 00 00 00 00
    dsx reselect e9 [0x00e9] 00 00 00 00 00 00
    poll F12 0x0006, 12 samples -> 00 00 00 00 00 00 00 00 (stray 04)
    irq 1 -> 0 (edge 1) ... irq 0 -> 1 (edge 15)

So: the one landing read still works and the 24-byte window is correct (the
F12 record really is `4c 00 13 06 01 12`), the cached repeat returns the tail
of the previous transfer (`1e 08 00 40 38 0e`), and the forced page select
turns the next read into zeros. But **IRQ GPIO 67 moves on every tap** while
F12 data stays zero. The controller is alive and sensing; it is not reporting
2D data.

That is exactly the vendor driver's wakeup-gesture (LPWG) state. The vendor
probe finds F01/F12 at 0.9 s, then suspends at 3.2 s with
`enable_wakeup_gesture is on`; a warm reboot inherits it. `synaptics_rmi4_resume()`
leaves it with two writes:

* `synaptics_rmi4_sleep_enable(false)`: F01 control `0x0D`, bits [2:0] =
  `NORMAL_OPERATION` (0), keeping `CONFIGURED` (bit 7) and the no-sleep bit;
* `synaptics_rmi4_f12_wg(false)`: read three bytes at `F12 ctrl 0x13 +
  ctrl20_offset` and write them back with `reporting_control[set_wakeup_gesture]
  = F12_CONTINUOUS_MODE` (`0x00`).

`0195-whyred-touch-wake-lpwg.patch` therefore:

* adds `dsx_write_f()` - START, address+W, register, data, STOP - and only
  sends `FF <page>` when the cached page really changes;
* sends **no page select at all**: `dsx_page = 0` before the first read, which
  is where F01 `0x0D`, F12 query `0x4C`, F12 ctrl `0x13` and F12 data `0x06`
  live;
* spends the one landing read on F01 control, derives the wake value as
  `(v & ~0x07u) | 0x80u`, and writes it back;
* scans the PDT again after that write, then dumps F12 data/query/ctrl, so the
  ring shows whether the write re-armed the address and whether the reporting
  mode really changed;
* in `dsx_f12_poll()`, sends the F01 normal-operation write before each of the
  12 samples instead of a page select, and prints `valid` when the
  finger-status bit 7 is set;
* drops the framing matrix, `dsx_identify()` and `dsx_page_probe()` from the
  touch path, because each of them spends the landing read; F12 comes from the
  fixed record instead.

The F12 query dump is the next input: its byte 4/5 presence map gives
`ctrl20_offset`, and query5 bit 3 (`ctrl27_is_present`) says whether byte 0 or
byte 2 of the reporting control is the gesture byte. 0196 will use that to
write continuous mode if 0195's `0x13` block is not the right address.

`tests/run_tests.sh` pins `dsx_write_f`, the four fixed addresses, the
`(v & ~0x07u) | 0x80u` wake value, `dsx_wake_normal()` before every sample,
the complete absence of `dsx_page = -1` and `dsx_reset(north)`, and the
removal of `dsx_diag`/`dsx_identify`/`dsx_page_probe` from the patch.

### 2026-11-12: 0195 proves the F01 write works and that it is not the wake

Ring 0195 (flush #221, console `shim-boot-touch-pdt-wake-console.img`) is the
first run with a register write on the bit-bang, and it answers two questions
at once:

    f01 ctrl first read 0x00
    f01 ctrl 0x000d <- 0x80 ack
    after wake pdt[0x00e9] 00 00 00 00 00 00 ... 00
    after wake: 1 entries, F12 missing
    dsx repeat cached [0x00e9] 00 00 00 00 00 00
    dsx reselect e9 [0x00e9] 00 00 00 00 00 00
    dsx f12 data after wake [0x0006] 00 00 04 00 00 00 04 00
    dsx f12 query [0x004c] 00 00 ... 00
    dsx f12 ctrl [0x0013] 00 00 ... 00
    poll 0..11 F12[06] 00 00 00 00 00 00 00 00 (stray 04)
    irq 1 -> 0 (edge 1) ... irq 0 -> 1 (edge 87)

So the bit-bang **can write**: every byte of `F01 control 0x0D <- 0x80` was
ACKed (the scan only ever ACKs 0x20, so the ACK sampling itself is sound).
The write is not the wake, though. Every read after it returns zero, including
a fresh PDT scan and the F12 query/control blocks, while IRQ 67 still moves on
every tap. Writing `CONFIGURED` into a part that is in wakeup-gesture mode does
not take it out of that mode.

The recovery driver shows the real order. It probes at 0.92 s and registers
`input2` (so the PDT is readable then), suspends at 3.2 s with
`enable_wakeup_gesture is on`, and its later `udg_scan_pdt` cannot find F12.
The vendor's error path for exactly this state is `synaptics_rmi4_sw_reset()`:
write `0x01` to the F01 **command** base (`0x06`, fixed by the RMI4 spec),
wait `reset_delay_ms`, then `synaptics_rmi4_query_device()` rescans the PDT
downwards from `0x00E9` in six-byte records. The command base is not the guess
the 0194 stream suggested (`2f 26 0d 04 01 01` is not a decodable F01 record);
F01's query/command/control/data/interrupt bases are fixed at
`00/06/0D/11/0E`.

`0196-whyred-touch-sw-reset.patch` therefore:

* adds `dsx_read_page()`, which always forces the two-byte page select
  (`FF 00`) before the addressed read, matching
  `synaptics_rmi4_i2c_read()`;
* issues the software reset (`F01 command 0x06 <- 0x01`) and waits 300 ms;
* reads the F01 device status (`0x11`) and then walks the PDT **downwards**,
  one addressed six-byte record at a time, taking the F01/F12 base addresses
  from the records and stopping at the `0x00` end marker instead of reading a
  fixed 24-byte window;
* only after that scan reads F01 control and sets `CONFIGURED` if it is still
  clear, so the 0195 mistake (write first, then scan) cannot repeat;
* dumps the F12 query and control blocks at the bases the scan found, which is
  the input for the reporting-mode write;
* page-selects before every F12 poll and touch-test sample, because after a
  real reset the vendor framing is the one that addresses the part.

If the reset ACKs and the walk returns a real F01 record, 0197 only has to
compute `ctrl20_offset` from the F12 query dump and write continuous reporting
mode. If the walk still returns zeros, the reset itself is refused in this
state and the next move is an early probe, before the 3 s suspend.

`tests/run_tests.sh` pins the reset write, the downward walk with a page
select per record, the F01 bases taken from the record, the scan-before-
configure order, and the removal of the fixed-address `dsx_wake_probe()` /
`dsx_pdt_scan()` path.

### 2026-11-13: what the fork found, and the F12 setup 0198 adopts

Checked the two forks of this repository for a working touch path:

* `tahamsaglam/ios-whyred2` is the Novatek NT36672 variant from 28 Oct and
  still reports "Touch: not yet enabled"; nothing to reuse.
* `akshayrathore110/ios-whyred2` is the only serious attempt (six commits,

  `SweetHIDTouch` yet, so the lock screen still ignores touch", it opened no
  touch PR, and its last commits are still adding F12 parsing - so no fork has
  confirmed working touch either.

It did, however, get three things right that this tree lacked, and `0198`
ports them from the **vendor reference driver** rather than from the fork
(two of the fork's details are wrong):

1. F12 must be parsed before it can be used. `query_5` (control presence) is
   at `query_base + 5`: byte 0 is `size_of_query6`, the rest are ctrl0..
   presence bits. `query_8` (data presence) is at `query_base + 8` with byte 0
   `size_of_query9`. The fork read these at offsets 4 and 7 *within* a 20-byte
   query block, which lands inside the size byte.
2. Reporting is **control 28**, and the vendor writes `RPT_DEFAULT` (`0x1F`:
   type + X/Y LSB/MSB) to it in `synaptics_rmi4_f12_set_enables()`. The fork
   wrote `0x01` and therefore enabled only the type bit.
3. The 2D finger data is at `data_base + data1_offset`, where
   `data1_offset = query_8->data0_is_present`. Data0 is the wakeup-gesture
   register and sits in front of the fingers. The fork added the count of
   *all* present data registers, which points past the finger block.

Control register offsets are the number of present registers below the target
(each control register is one byte); the vendor spells this out for ctrl_8,
ctrl_20, ctrl_23, ctrl_28, ctrl_31 and ctrl_58. `0198` only needs ctrl_28.

`0198-whyred-touch-f12-reporting.patch` therefore adds `dsx_f12_program()` and
calls it right after the early PDT dump:

* refuses to program unless the PDT proves it is real - F01 must be the
  standard `00 06 0D 11` record. The shifted byte stream that all late probes
  saw can fake a `fn 0x12` record, so "F12 found" alone is not enough;
* reads the query_5/query_8 sizes and presence bytes, prints them, computes
  ctrl28 and the touch data register, and writes `0x1F` to ctrl28 with a
  read-back;
* stores the computed registers and uses them for the F12 poll and the late
  touch test (the late probe falls back to a late reset + program when
  `sweetouchearly` is off);
* keeps every diagnostic line in the ring, including the F01 record, the
  query bytes, ctrl28 read-back and the chosen data register.

If the early window is real, this boot should print `F01 ... 00 06 0d 11`,
`f12 ctrl28 <- 0x1f ack` and a read-back of `0x1f`, then the late poll should
show touch data changing with a finger. If the window is not real, the gate
prints `not programming F12` and the ring still contains the full early dump
that tells us where the part really is.

### 2026-11-14: the touch really is the Synaptics at 0x20, not the Novatek

The recovery DT enables both touch nodes (`synaptics_dsx@20` with no `status`
property, `novatek@62` with `status = "ok"` and `novatek,reset-gpio = 66`),
and the Novatek probe fails with `-16` because the Synaptics driver already
owns the shared IRQ GPIO 67. That looked like proof the real part was the
Novatek and the 0x20 device was a ghost. It is the other way round.

Read-only checks in recovery say so:

* GPIO 66 (the Novatek reset) is already high at rest: exporting it as an
  input reads `1`, so the Novatek is out of reset and still does not ACK.
  Pulsing it low/high changes nothing, and `0x62` never answers a scan.
* `0x20` ACKs on every bus scan, and at cold boot the vendor driver used it
  successfully: it walked the PDT, logged `input: synaptics_dsx as input2` at
  0.921 s, found the F34 image records and compared firmware IDs. Garbage
  from 0x20 only appears through raw `/dev/i2c-1` reads *after* the driver has
  suspended the part into wakeup-gesture mode (the driver itself logs
  `I2C retry` on resume), so those reads prove nothing about identity.
* The `0x04..0x07` ACKs in the recovery scan are noise from the QUP adapter,
  not devices: the bit-bang scan in XNU finds exactly one address, `0x20`.

So the DSX work stays on `0x20`; the Novatek node is an unused variant entry
and `novatek,reset-gpio` must not be pulsed again. The remaining problem is
unchanged and is a timing one: the vendor driver owns the chip in the
0.9-3.2 s window after boot, and XNU's probe runs after eMMC init.

### 2026-11-14: 0203 panic is a `%s%s` bug, not a hang in take-over

The 0203 boot painted the touch bands to white and then panicked. The dump
the user transcribed:

```
esr: 0x96000005  far: 0x0000000000000001
pc:  0xfffffe00073695b4  lr: 0xfffffe00073695c8
x23: 0x0000000000000001  x19: 0  x26: 0
```

The repo-local kernel is a Mach-O whose `__TEXT` starts at
`0xfffffe0007004000`, not at `0xfffffff007...`:

```
llvm-symbolizer --obj=/tmp/opencode/xnu-kernel.43545987044 0xfffffe00073695b4
-> vprintf_internal
```

Disassembly at that address is `ldrsb w0, [x23, x26]`, i.e. `*("%s" arg)`
with `x23 = 1`. So the format string asked for one more `%s` than the call
supplied, and the missing argument was register value `1`. That is exactly
`santoni_touch_early()`:

```c
printf("WHYRED TOUCH: early done at %llu ms, F12 %s%s",
    (unsigned long long)dsx_early_end_ms, dsx_f12_found ? "found" : "missing");
```

Two `%s`, one string, and the abort happens before the probe's `return`, so
`TOUCH_PHASE_MARK(0, ...)` and the whole eMMC take-over never ran. This also
explains why the ring always stayed at `flush #208`: the panic precedes
`santoni_log_start()`.

0204 replaces the format with a single `%s` and a comment; the remaining
suffix lines are already separate `printf()` calls. The white band in 0203
was therefore the last touch band, not a phase band - the bright colours
were never reached.

Band readout rule from now on: white is band 19 and means "early probe
finished the F12 setup"; the phase bands only start *below* it, after the
fixed printf returns.

### 2026-11-19: 0206 resets at the PDT's own F01 base

The 0205 ring ended the guessing. The raw `f01scan` rows merge into a single
536-byte stream that the part repeats: F34 `27 00 09 00 21 34`, F01
`2f 26 0d 04 01 01`, F12 `4c 00 13 06 01 12`, an end marker, then the same
bytes again. Function records in a running RMI4 stream are back to back, so
the F01 command base on this unit is `0x26` and its control base is `0x0d`.
The literal `00 06 0d 11` never appears, which is why 0204's gate and 0205's
signature scan both came up empty; 0205 still wrote the reset command to
`0x06`, which is F12's **data** register.

0206 reorders the probe. It reads two back-to-back `0x200` windows, because
the pointer position is unknown and the cycle is 536 bytes, so one window can
miss a record that straddles its end. It finds the F12 record by its full six
bytes, takes the nearest F01 record that has function number `0x01` and
control `0x0d`, and stores those bases. The
reset then writes `0x01` to the record's command base (`0x26`), with `0x06`
kept only as a fallback for a part that reports no stream at all. A
`dsx_addr_works()` helper reads two PDT registers twice: identical bytes mean
the address phase is honoured, sequential bytes mean the part still streams. The
walk, F12 query/programming and the poll run only when addressing works, and
every F12 register read uses the vendor's cached page form, so no `FF <page>`
is sent between registers.

`tools/dsx-pdt.py` now also locates the F34/F01/F12 triplet, names the
stream phase and prints the bases the probe must use; the test suite builds a
64-byte-row synthetic stream for it.

### 2026-11-19: the recovery probe shows pure streaming, no addressing

Running `tools/i2cprobe` against the vendor-bound DSX in OrangeFox (QUP, the
same bus the working driver uses) settles the framing question. While a
finger was held down, every mode (page select or not, repeated start or
stop, dummy byte or not, even a plain read with no address) returned one
continuous byte stream, each read advancing the pointer by exactly its
length. Aligned, the stream is `ff x7`, F34 `27 00 09 00 21 34`, F01
`2f 26 0d 04 01 01`, F12 `4c 00 13 06 01 12`, then zeros.

So no framing re-seeks the chip while it is in this state. The vendor
driver's own F01/F34 reads are sane (`productinfo 0x01 0x00`, buildid
`2788281`, fwblockcount `432`), which means those reads happen while the
chip is still addressable, i.e. before it suspends into wakeup gesture
mode at ~4.8 s. After that it only wakes on a touch IRQ and stays in the
streaming state.

That points at the boot history, not at the framing: a warm reboot from
Android inherits LPWG, and the F01 reset cannot be delivered because the
chip no longer accepts an address. A true cold boot (full power-off) is
the cheap test before changing the driver again.

### 2026-11-21: the Linux whyred tree gives the DSX no reset line

The vendor kernel source settles the GPIO question. Xiaomi's
`whyred-o-oss` (`MiCode/Xiaomi_Kernel_OpenSource`, `efbbb9c`) and

* Synaptics DSX: `0x20`, IRQ GPIO 67, `vcc_i2c` = `pm660_l11`, UB address

* Novatek NT36672: `0x62`, reset GPIO 66, IRQ GPIO 67.

only reset paths are the F01 command and the rail.

repeated-start read. That leaves the state of the part, not the framing,
as the difference between Android and this port.
